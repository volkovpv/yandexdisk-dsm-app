# Yandex Disk (ARM) для Synology DSM

ARM64-версия пакета для устройств Synology на процессорах **aarch64 / ARMv8** —
в первую очередь **DS124** (Realtek RTD1619B).

---

## ❓ Почему отдельная ARM-сборка и при чём тут rclone

Официальный консольный клиент `yandex-disk` собирается Яндексом **только под
x86** (amd64/i386) — ARM-сборки не существует и исходников нет. Поэтому на
ARM-моделях (DS124 и др.) исходный x86_64-пакет выдаёт «пакет не поддерживается
платформой», а если подменить только поле `arch` — бинарник всё равно не
запустится (`Exec format error`).

В этой сборке движок синхронизации заменён на **`rclone`** — open-source
(MIT) с нативной сборкой под `linux/arm64` и встроенной поддержкой Яндекс Диска.
Чтобы сохранить интерфейс DSM и существующие скрипты, команда `yandex-disk`
оставлена как **обёртка** (`start|stop|status|sync|setup`), работающая поверх
`rclone bisync` (двусторонняя синхронизация — ближайший аналог демона
yandex-disk).

| | x86_64-версия | ARM-версия (эта) |
|---|---|---|
| Движок | `yandex-disk` (proprietary) | `rclone` v1.74.3 (open-source) |
| Архитектура | x86_64 | aarch64 / ARM64 |
| Команда `yandex-disk` | нативный бинарник | sh-обёртка над `rclone` |
| Авторизация | `yandex-disk token` | OAuth через `rclone authorize` |
| Синхронизация | демон yandex-disk | периодический `rclone bisync` |
| Размер `.spk` | ~5–7 МБ | ~23 МБ (rclone — статический Go-бинарник) |
| UI (DSM) | статус, логи, очистка | то же **+ полная настройка** (папка, токен, запуск) без SSH |

## 🖥 Поддерживаемые модели

Поле `arch` пакета: `rtd1619b rtd1296 armada37xx armada38x alpine4k`.

### ✅ 64-битные (aarch64) — полностью поддерживаются
| Платформа | Модели (примеры) |
|---|---|
| **rtd1619b** | **DS124**, DS223j, DS223, DS123 |
| **rtd1296** | DS118, DS218, DS218play, DS418, DS420j |
| **armada37xx** | DS120j, DS220j, DS119j |

### ⚠️ 32-битные (armv7) — НЕ запустят arm64-бинарник
`armada38x` (DS116, DS216j, DS216se, RS217) и `alpine4k` (DS416, DS216, DS715)
включены в `arch` для совместимости установки, но это 32-битные процессоры —
нативный **arm64** rclone на них работать не будет. Для них нужна отдельная
сборка rclone под `linux-arm` (armv7) (потенциальное будущее улучшение:
вложить оба бинарника и выбирать по `uname -m`).

**Целевое устройство этой сборки — DS124 (rtd1619b, aarch64).**

## 🔧 Установка

1. **DSM → Центр пакетов → Установка вручную** → загрузите `YandexDisk-ARM-<версия>.spk`
   (например `YandexDisk-ARM-1.1.0.spk` — файл со страницы GitHub Releases).
   Подтвердите установку при предупреждении об «неизвестном издателе».
   После установки пакет показывает статус **«Запущено»** и ждёт настройки.
   Резидентного sync-демона в пакете нет — синхронизация не начнётся, пока вы не
   настроите её в интерфейсе пакета (папка + токен) и не добавите задачу в
   Планировщик задач (см. ниже).
2. **Права на папку синхронизации.** Пользователь `sc-yandexdisk` создаётся
   **автоматически самим DSM** при установке (в DSM 7 это «системный внутренний
   пользователь»; команды `synouser`/`synogroup` в пакетах запрещены).
   Панель управления → Папка общего доступа → ваша папка → Изменить →
   Разрешения → в выпадающем списке выберите **«Системный внутренний пользователь»**
   → найдите `sc-yandexdisk` → дайте **чтение/запись**.
   Проверить, что пользователь создан: по SSH `id sc-yandexdisk`.

## 🔑 Первоначальная настройка (в интерфейсе DSM, без SSH)

Начиная с версии **2.0.0** пакет настраивается **полностью из интерфейса** в DSM —
SSH больше не нужен. Понадобится только **компьютер с браузером**, на котором
**установлен `rclone`** (https://rclone.org/downloads/), — один раз, чтобы получить
OAuth-токен.

### Шаг 1. Дайте `sc-yandexdisk` права на папку
Пользователь `sc-yandexdisk` создаётся **самим DSM** при установке. Панель
управления → Папка общего доступа → ваша папка → Изменить → Разрешения → в
выпадающем списке выберите **«Системный внутренний пользователь»** → найдите
`sc-yandexdisk` → дайте **чтение/запись**. Если прав не хватит, интерфейс пакета
подсветит это при проверке папки.

### Шаг 2. Откройте пакет и добавьте папку
В Центре пакетов откройте **Yandex Disk** и нажмите **«Добавить папку»**. В диалоге:

- **Локальная папка** — абсолютный путь (например `/volume1/yandexdisk`); поле
  сразу показывает, существует ли папка и доступна ли она для записи `sc-yandexdisk`;
- **Удалённый ресурс** — по умолчанию `yandexdisk:`, можно подпапку
  `yandexdisk:/Backup` (имя `yandexdisk` фиксировано — меняется только подпапка);
- **Чистка thumbs** — по желанию (удалять `Thumbs.db`/`.DS_Store` перед синхронизацией;
  `@eaDir` намеренно не трогается, чтобы не воевать с индексатором Synology).

### Шаг 3. Получите токен (на компьютере с браузером)
На компьютере с браузером выполните:
```sh
rclone authorize "yandex"
```
Откроется браузер → войдите в Яндекс и разрешите доступ. rclone напечатает токен между маркерами:
```
Paste the following into your remote machine --->
{"access_token":"y0_Ag...","token_type":"OAuth","refresh_token":"...","expiry":"..."}
<---End paste
```
Скопируйте строку `{ ... }` **целиком** (вместе с фигурными скобками), вставьте её в
поле секции **«Подключение к Яндекс Диску»** и нажмите **«Подключить»**. После
сохранения токен нигде не отображается — только индикатор **«Подключено ✓»**
(секрет пишется в `rclone.conf` `0600`, не попадает в логи/ответы).

### Шаг 4. Сохраните и синхронизируйте
Нажмите **«Сохранить»**, затем **«Синхронизировать сейчас»**.

> ⚠️ Первый запуск выполняет `rclone bisync --resync` — создаётся базовая точка
> двусторонней синхронизации. Убедитесь, что в локальной папке и на Диске именно то,
> что нужно объединить, иначе файлы могут «склеиться» в обе стороны.

### Шаг 5. Расписание
Резидентного демона нет — периодический запуск настраивается в **Планировщике
задач DSM** (см. раздел «Расписание синхронизации» ниже). Диалог настройки
показывает готовую к копированию команду задачи.

> 💡 При **обновлении** пакета ранее заданные папка, remote и токен сохраняются —
> открыв пакет, вы увидите их уже заполненными, настраивать заново не нужно.

## 🖧 Настройка по SSH (запасной / диагностический путь)

Терминал для настройки больше **не обязателен**, но остаётся удобен для
диагностики и автоматизации. Полный пошаговый справочник команд (включая мастер
`yandex-disk setup`) — в [`docs/terminal-setup.md`](docs/terminal-setup.md). Кратко
те же действия делают подкоманды обёртки (всё — от имени `sc-yandexdisk`, тот же
код, что вызывает UI):

```sh
# 1) подключить OAuth-токен (JSON со stdin — не виден в `ps`):
printf '%s' '<JSON-ТОКЕН>' | sudo -u sc-yandexdisk /usr/local/bin/yandex-disk set-token
# 2) задать локальную папку и remote (3-й арг. clean_thumbs 0|1 — опционально):
sudo -u sc-yandexdisk /usr/local/bin/yandex-disk set-folder /volume1/yandexdisk yandexdisk:
# 3) первая синхронизация и проверка состояния:
sudo -u sc-yandexdisk /usr/local/bin/yandex-disk sync     # первый прогон делает --resync
sudo -u sc-yandexdisk /usr/local/bin/yandex-disk status   # должно стать idle/ok
```

> `set-folder` сам валидирует ввод (абсолютный путь, формат remote) и пишет
> `config.cfg` атомарно. Если правите `config.cfg` вручную — комментарий `#` только
> на отдельной строке, не после значения (иначе sync падает с `rc=7`).

## 🧩 Команды обёртки `yandex-disk`

| Команда | Действие |
|---|---|
| `yandex-disk sync` | синхронизировать сейчас (эту команду вызывает Планировщик задач) |
| `yandex-disk status` | последнее состояние синхронизации (читается в UI пакета) |
| `yandex-disk setup` | помощник настройки OAuth/конфига (SSH-мастер; в UI не нужен) |
| `yandex-disk set-folder <dir> [remote] [clean_thumbs]` | задать папку/remote в `config.cfg` (атомарно); этим пользуется UI |
| `yandex-disk set-token` | сохранить OAuth-токен (JSON со stdin) в `rclone.conf` `0600`; этим пользуется UI |
| `yandex-disk get-config` | показать текущий конфиг (без значения токена — только флаг «настроен») |
| `yandex-disk check-folder <dir>` | проверить папку: существует / доступна на запись / владелец |
| `yandex-disk version` | версия rclone |
| `yandex-disk rclone <args…>` | прямой вызов rclone с конфигом пакета |
| `yandex-disk start` / `stop` | без эффекта — резидентного демона нет, период задаётся в Планировщике |

> Резидентного демона в пакете **нет** (на DSM 7 он ненадёжен). Периодический запуск —
> через Планировщик задач DSM (см. раздел «Расписание синхронизации»).
>
> Первый `yandex-disk sync` делает `rclone bisync --resync` (создаёт базовую точку
> двусторонней синхронизации). Убедитесь, что в локальной папке и на Диске именно то,
> что нужно объединить. При конфликте (файл изменён с обеих сторон) выигрывает
> **локальная** копия — `--conflict-resolve path1`; версия с Диска при этом не теряется,
> а сохраняется рядом как переименованная копия.

## ⏰ Расписание синхронизации (важно для DSM 7)

Резидентного sync-демона в пакете нет: под управлением systemd в DSM 7 он **ненадёжен**
(может «уснуть» после первого прогона, а пакет показывается остановленным). Поэтому
периодическую синхронизацию настраивают через **Планировщик задач DSM**:

1. **Панель управления → Планировщик задач → Создать → Запланированная задача → Пользовательский сценарий.**
2. **Общие:** имя `YandexDisk sync`; пользователь **root**.
3. **Расписание:** ежедневно, периодичность — **каждые 5 минут** (или по вкусу).
4. **Настройки задачи → Выполнить команду:**
   ```sh
   sudo -u sc-yandexdisk /usr/local/bin/yandex-disk sync
   ```
   (`HOME` обёртка выставляет сама, доп. переменные не нужны.)
5. Сохранить.

Команда `yandex-disk sync` уже включает `--inplace`, `--max-lock`, `--recover` и
само-восстановление базы (`--resync` при потере списков), так что задача устойчива
к прерываниям и зависшим блокировкам. Параллельные запуски исключены: `sync` берёт
неблокирующий `flock` (`var/sync.lock`) — если предыдущий прогон ещё идёт, новый
тихо завершается с «sync already running, skip».

> 📄 Подробный вывод последней синхронизации пишется в
> `/var/packages/YandexDisk/var/logs/rclone.log` и виден в UI на вкладке
> **«Синхронизация»** (последние 300 строк) — туда и смотрите при ошибке (`rc=N`),
> а не только в историю статусов на вкладке «Лог». Лог `rclone.log` и история
> статусов автоматически ротируются по размеру (>1 МБ → `.1`), не разрастаясь.

### Исключите папку из фоновых служб Synology
Чтобы индексация/антивирус не трогали временные файлы синхронизации:
- **Панель управления → Индексирование** (и Медиа-сервер / Universal Search) — уберите
  папку синхронизации из индексируемых.
- Если установлен **Antivirus Essential** — исключите эту папку из проверки.

## 🛠 Сборка пакета

`.spk` и бинарник `rclone` **не хранятся в git** — они раздаются как **GitHub
Release assets** и собираются из исходников. В имя `.spk` подставляется версия из
`spk/INFO`, например `YandexDisk-ARM-1.1.0.spk`, — так ассеты релиза
самоописательны и ревизии не перезаписывают друг друга.

> Версии — по семантическому версионированию `МАЖОР.МИНОР.ПАТЧ` (изменение разряда
> обнуляет всё правее); подробнее — в `CHANGELOG-ARM.md`, раздел «Версионирование».

### Локальная сборка

Нужны: `bash`, `tar`, `gzip`, `unzip`, `curl` (или `wget`), `sha256sum`;
опционально `dash`, `shellcheck`, `python3` — для статических проверок.

```sh
./build.sh
```

`build.sh` по шагам:
1. **Статические проверки** всех скриптов пакета (`dash -n` + `shellcheck`) и
   валидация JSON `conf/privilege`.
2. **Докачивает `rclone`** (если `spk/package/rclone` отсутствует) с
   `downloads.rclone.org` и сверяет **SHA-256** zip и распакованного бинарника
   (zip кэшируется в `downloads/`, вне git); проверяет, что бинарник — AArch64.
3. **Собирает** `YandexDisk-ARM-<версия>.spk` (+ `.sha256`). Сборка
   **воспроизводима байт-в-байт** (фиксированные mtime + `gzip -n`), поэтому
   контрольная сумма повторяется при чистой пересборке.

Проверить готовый файл:

```sh
sha256sum -c YandexDisk-ARM-<версия>.spk.sha256
```

### Сборка и релиз через GitHub Actions

Workflow `.github/workflows/build-spk.yml`:

- **на каждый push/PR любой ветки** — собирает `.spk` и гоняет все гейты
  (герметика, покрытие, статические проверки, воспроизводимость); готовый `.spk`
  доступен как **workflow artifact** во вкладке **Actions** (валидация без
  публикации);
- **на push в `main`** (т.е. после мержа PR) — дополнительно **публикует**
  версионный `.spk` + `.sha256` как **ассеты GitHub Release** `v<версия>`.
  Версия берётся из `spk/INFO`; публикация **идемпотентна** — релиз создаётся
  только если версия поднята (релиза `v<версия>` ещё нет). Мержи без bump версии
  (правки доков/тестов и т.п.) релиз не плодят.

Выпуск новой версии — просто поднять версию в одном PR и смержить его в `main`:

```sh
# 1. поднять версию синхронно в spk/INFO + CHANGELOG-ARM.md + RELEASE-INFO-ARM.txt
#    (гейт check-version-drift.sh не даст разъехаться);
# 2. открыть PR, дождаться зелёного CI, смержить в main.
```

После мержа GitHub Actions соберёт `YandexDisk-ARM-<версия>.spk`, создаст тег
`v<версия>` на мерж-коммите и приложит `.spk` + `.sha256` к новому Release —
скачать готовую сборку можно со страницы
[Releases](https://github.com/volkovpv/yandexdisk-dsm-app/releases). Заметки
релиза берутся из секции версии в `CHANGELOG-ARM.md`. Ручной повтор публикации
(если первый прогон упал) — кнопка **Run workflow** (workflow_dispatch) на ветке
`main`; та же защита от дублей делает это безопасным.

## ⚠️ Важно

- Синхронизация через `rclone bisync` логически эквивалентна, но **не идентична**
  оригинальному демону yandex-disk. Функциональная синхронизация с живым
  аккаунтом проверяется на самом NAS (скрипты выше) — на этапе сборки
  проверяется только структура пакета и корректность скриптов.
- Движок `rclone` — сторонний open-source проект: https://rclone.org
  (бэкенд Yandex Disk: https://rclone.org/yandex/).
