## 1. Контекст: что сегодня делается по SSH

Текущая первичная настройка (из `README.md`, `spk/INFO:description_rus`,
`docs/terminal-setup.md`, обёртки `spk/package/yandex-disk`) состоит из шести
шагов. Ниже — инвентаризация и судьба каждого шага в новой схеме.

| # | Сейчас (как делается) | Где делается | Судьба в новой схеме |
|---|---|---|---|
| 1 | Права rw на папку для `sc-yandexdisk` | DSM GUI (Панель управления → Общая папка) | Остаётся в GUI. UI **детектит** отсутствие прав и подсказывает, что сделать (не SSH). |
| 2 | Получение OAuth-токена `rclone authorize "yandex"` | ПК с браузером | **Tier 1:** одна команда на ПК → вставка JSON в форму UI. **Tier 2 (опц.):** вход через Яндекс прямо из UI (см. §3.2). |
| 3 | `yandex-disk setup` + мастер `rclone config` | SSH на NAS | **Убирается.** Создание remote `yandexdisk` — кнопкой в UI (см. §3.2, §3.4). |
| 4 | Запись `config.cfg` (`dir`, `remote`, `clean_thumbs`) через `tee`/`vi` | SSH на NAS | **Убирается.** Поля формы в UI (см. §3.4). |
| 5 | Первый `yandex-disk sync` (`--resync`) | SSH на NAS | **Убирается.** Кнопка «Синхронизировать сейчас» в UI. |
| 6 | Задача в Планировщике задач DSM | DSM GUI (Планировщик задач) | Остаётся в GUI (это **не SSH**). UI даёт точную команду/подсказку; авто-создание — отдельный вопрос (см. §3.3). |

**Вывод.** Из шести шагов реально «по SSH» выполняются только 3–5. Их перенос в
UI закрывает цель «без SSH». Шаги 1 и 6 уже выполняются в графическом интерфейсе
DSM, а не по SSH; UI лишь делает их явными и помогает их выполнить. Единственное
действие, которое в минимальной версии (Tier 1) остаётся вне UI пакета, — запуск
`rclone authorize "yandex"` на ПК с браузером (это **не** SSH к NAS); Tier 2
устраняет и его.

## 2. Целевой пользовательский сценарий

После установки и открытия пакета пользователь попадает на новую вкладку
**«Настройки»** и проходит линейный мастер:

1. **Шаг «Папка».** Поля: локальная папка (`dir`), удалённый ресурс (`remote`,
   по умолчанию `yandexdisk:`, можно подпапку), флаг `clean_thumbs`. UI проверяет,
   что папка существует и доступна `sc-yandexdisk` на запись; если нет — понятная
   подсказка про права общей папки (шаг 1 из §1).
2. **Шаг «Подключение к Яндекс Диску».**
   - *Tier 1:* инструкция «выполните на ПК `rclone authorize "yandex"`» + поле
     для вставки JSON-токена + кнопка «Подключить».
   - *Tier 2 (опц.):* кнопка «Войти через Яндекс» → OAuth прямо в браузере админа.
3. **Шаг «Первая синхронизация».** Кнопка «Синхронизировать сейчас» (предупреждение
   про `--resync`: содержимое папки и Диска будет слито в обе стороны).
4. **Шаг «Расписание».** Подсказка по созданию задачи в Планировщике задач DSM
   (готовая к копированию команда + ссылка), либо авто-управление расписанием —
   в зависимости от решения по §3.3.

**При обновлении пакета** пользователь, открыв «Настройки», видит уже
заполненные `dir`/`remote`/`clean_thumbs` и индикатор «Яндекс Диск подключён ✓»
(см. §3.5) — ничего настраивать заново не нужно.

## 3. Ключевые технические вызовы и решения

### 3.1. Привилегии CGI — главный риск, требует проверки на NAS

**Проблема.** Конфиги принадлежат пользователю пакета `sc-yandexdisk`
(`conf/privilege`: `run-as: package`), причём `rclone.conf` хранит OAuth-токен и
должен быть `0600`. Чтобы UI мог их писать, исполняющий CGI процесс должен иметь
права на запись в `home/.config/...`. В DSM 7 пакеты работают **от пользователя
пакета, не от root** (root требует подписи Synology), а исполнение
сторонних CGI под `/webman/3rdparty/<pkg>/` исторически зависит от версии DSM:
встречаются варианты «от `http`» и «от root».

**Что уже известно из кода.** Существующий `clear_log.cgi` сегодня успешно
делает `: > status_history.log` в `var/logs/` (файл пакета) — значит текущий CGI
**способен писать файлы пакета**. Но права на `home/.config` (особенно `0600`
`rclone.conf`) могут отличаться от `var/logs`.

**Решение — Phase 0 (спайк на NAS).** До любой реализации эмпирически выяснить:
из CGI вывести `id`, `whoami`, и попытаться записать тестовый файл в
`home/.config/yandex-disk/` и `home/.config/rclone/`. По результату — одна из веток:

- **Ветка A (CGI пишет как `sc-yandexdisk`/root):** прямой путь. CGI делегирует
  запись обёртке `yandex-disk` (см. §4) — она пишет конфиги штатно.
- **Ветка B (CGI пишет как `http`/иначе, прав нет):** нужен привилегированный
  посредник. Кандидаты (выбор — после спайка, см. §11 «Открытые вопросы»):
  - resource-worker / sanctioned-механизм DSM 7 для привилегированных операций;
  - setuid/`set-capability`-обёртка из `package.tgz` (через `conf/privilege`),
    запускающая узкий валидированный helper от имени `sc-yandexdisk`;
  - spool-схема: CGI кладёт валидированный «запрос на применение» в каталог,
    доступный обоим пользователям, а уже резидентный `yandex-logger` (работает от
    `sc-yandexdisk`) его применяет. Минус — задержка и усложнение; рассматривать
    только если A/первые два варианта недоступны.

> ⚠️ Это **NAS-only** пункт (`CLAUDE.md` → «изменение, которое проверяется только
> на реальном NAS»). План ниже написан под **ветку A** как основную; ветка B
> добавляет привилегированный посредник, но **не меняет** контракт обёртки и тесты.

> ⛔ **ОПРОВЕРГНУТО 2026-06-20.** Повторный запуск `diag.cgi` тем же способом (webman,
> браузер) дал `euid=256139` — CGI исполняется как **сам пользователь пакета
> `sc-yandexdisk`** (`run-as: package`), а НЕ root. Вывод «root» ниже — ошибочный; на
> нём построили `sudo -u sc-yandexdisk`, что и вызвало баг 2.0.x: `sc-yandexdisk` не
> может беспарольно sudo → в synoscgi sudo зависает → дашборд падал в HTTP 500 (и запись
> не работала). **Актуальная ветка A в простейшем виде:** CGI пишет/читает конфиги и
> запускает sync **НАПРЯМУЮ** (файлы сразу `sc-yandexdisk`-овые, без root, без `chown`,
> без `sudo`). См. CHANGELOG `[2.0.1]`, тест T44, гейт `check-ui-contract.sh` (запрещает
> `sudo` в `settings.cgi`). Блок ниже сохранён как исторический (неверный) вывод спайка.
>
> ✅ **Результат спайка (2026-06-14, через webman, браузер).** CGI под
> `/webman/3rdparty/YandexDisk/scripts/diag.cgi` исполняется как **root**
> (`whoami: root`, `euid: 0`); обе цели — `home/.config/yandex-disk` и
> `home/.config/rclone` — **доступны на запись** (пробный файл создан `root:root`,
> `0644`). **Вердикт: ветка A** (прямая запись, без привилегированного посредника).
> Инструмент спайка: подкоманда `yandex-disk diag` + тонкий `diag.cgi` (логика
> покрыта герметикой T24–T27 + golden G5; см. §8).
>
> **Следствие для Phase 1 (важно).** CGI — root, а периодический sync исполняется
> как `sc-yandexdisk` (`sudo -u sc-yandexdisk yandex-disk sync`). Конфиги,
> записанные «как есть» под root, получат владельца `root`: `rclone.conf` режимом
> `0600 root:root` будет **нечитаем** для `sc-yandexdisk`, и sync сломается. Значит
> запись конфигов обязана давать файлы, **владелец которых `sc-yandexdisk`**.
> **Решение Phase 1 (§11.1):** CGI(root) делегирует со **сбросом привилегий** —
> `sudo -u sc-yandexdisk yandex-disk set-folder|set-token` (файлы сразу
> `sc-yandexdisk`-овые, рабочий `0600`, без root-owned секретов — наименьшая
> привилегия). Запись под root с `chown sc-yandexdisk` внутри
> `write_cfg_atomic`/`set-token` — отвергнутый fallback (есть момент root-владения
> секретом); применять только если сброс привилегий на NAS окажется недоступен.
>
> **Безопасность.** Раз 3rdparty-CGI здесь root, чек-лист §3.4 (валидация
> `dir`/`remote`/токена, токен не в argv) и §4 (мутации только из
> аутентифицированной админ-сессии DSM) — **критичны**: инъекция в root-CGI =
> компрометация root.

### 3.2. OAuth-токен Яндекс Диска

Бэкенд `yandex` в rclone имеет **встроенные** `client_id`/`client_secret`
(в мастере они оставляются пустыми) — пользователю **не нужно** регистрировать
своё приложение. На NAS нет браузера, поэтому токен добывается там, где браузер
есть.

- **Tier 1 (рекомендуемый MVP, минимальный риск).** Продуктизируем уже
  документированный «путь без мастера» (см. `README.md` → «Альтернатива без
  мастера»): пользователь на ПК выполняет `rclone authorize "yandex"`, копирует
  строку `{...}` и вставляет в поле UI. Обёртка создаёт remote командой, которая
  **уже** есть в `setup`-выводе обёртки:
  `rclone config create yandexdisk yandex token '<JSON>' --config <RCLONE_CONF>`.
  Плюсы: не требует регистрации приложения, опирается на проверенный путь,
  полностью покрывается герметичными тестами через `fake-rclone`.

- **Tier 2 (опционально, после Tier 1).** Вход через Яндекс прямо из UI (UI
  открыт в браузере админа — браузер есть!). Варианты:
  - OOB-флоу: зарегистрировать OAuth-приложение этого проекта с
    redirect на «страницу подтверждения» Яндекса, которая показывает код/токен;
    пользователь копирует его в UI (промежуточный CGI меняет код на токен).
  - Полный redirect-флоу на CGI-callback NAS.
  Минусы/вопросы: встраивание `client_id`/`client_secret` в открытый пакет,
  зависимость от стороннего OAuth-приложения, обмен кода на токен сетевым
  запросом из CGI — **требует решения человека** (см. §11) и проверки на NAS.

### 3.3. Расписание синхронизации

Канон: «Нет резидентного демона: синхронизацию запускает DSM Task Scheduler»;
возврат резидентного демона — пункт «остановись и спроси». Программное создание
задачи Планировщика требует root (`synoschedtask`) и/или неподдерживаемой правки
системной БД задач — это вне привилегий пакета и хрупко.

Опции (выбор — решение человека, §11):

- **Опция A (рекомендуемый MVP, в рамках канона, нулевой риск).** Расписание
  остаётся ручным шагом **в GUI** (Планировщик задач) — это **не SSH**. UI
  показывает готовую к копированию команду
  `sudo -u sc-yandexdisk /usr/local/bin/yandex-disk sync`, краткую инструкцию и,
  по возможности, ссылку на Планировщик задач; плюс кнопка «Синхронизировать
  сейчас». Цель «без SSH» при этом достигнута.
- **Опция B (требует одобрения, затрагивает инвариант «нет демона»).** Дать в UI
  поле «интервал» (ключ `interval` в `config.cfg`, исторически зарезервирован) и
  поручить триггер уже резидентному `yandex-logger` (он и так работает от
  `sc-yandexdisk`): по интервалу вызывать тот же `yandex-disk sync`. Это **не**
  новый sync-демон (долгий bisync по-прежнему запускается отдельным короткоживущим
  процессом, защищён `flock`), но формально размывает инвариант — **нужно явное
  одобрение**.
- **Опция C (требует одобрения + спайк).** Авто-создание задачи Планировщика из
  root-скрипта установки (`postinst`/`start-stop-status` выполняются от root).
  Неподдерживаемый API, хрупко, только NAS-валидация.

### 3.4. Безопасная запись конфигов

- **Токен не попадает в argv.** `rclone config create ... token '<JSON>'` кладёт
  секрет в командную строку (виден в `ps` другим процессам). **Решение (§11.4):**
  в ветке A обёртка пишет `rclone.conf` **напрямую** как INI
  (`[yandexdisk]\ntype = yandex\ntoken = <JSON>\n`) под `umask 077`, не передавая
  секрет аргументом; `rclone config create` не используется. *(NAS-валидация (§8):
  убедиться, что rclone принимает рукописный conf — для `yandex` со встроенным
  client этого достаточно; fallback на `config create` с передачей токена через
  временный файл/stdin, не через argv, — только если проверка на NAS провалится.)*
- **Права.** `rclone.conf` — `0600`, `config.cfg` — `0644`/`0600`, владелец
  `sc-yandexdisk`. Запись **атомарна**: во временный файл рядом + `mv` (нет
  «полузаписанного» конфига при сбое).
- **Валидация ввода** (защита и от инъекций, и от молчаливой порчи парсера
  `cfg()`):
  - `dir`: абсолютный путь (`^/...`), без символов перевода строки, **без
    подстроки ` #`** (парсер `cfg()` срезает инлайн-комментарий — путь с ` #`
    молча обрежется), существует/создаётся и доступен `sc-yandexdisk` на запись;
  - `remote`: `^[A-Za-z0-9_-]+:(/.*)?$`, по умолчанию `yandexdisk:` (имя
    `yandexdisk` — контракт канона);
  - `clean_thumbs`: только `0|1`;
  - токен: парсится как JSON и содержит `access_token`.
- **Токен — никогда в лог/ответ/stdout.** Ответы UI и история не содержат секрета
  (инвариант `CLAUDE.md`).

### 3.5. Сохранение существующих настроек при обновлении

- `config.cfg` и `rclone.conf` **уже** переживают обновление: `preupgrade`
  складывает `home/.config` в `$SYNOPKG_TEMP_UPGRADE_FOLDER`, `postupgrade`
  восстанавливает «если не выжило» (restore-if-missing). **Дополнительной работы
  по сохранению не требуется** — это и есть гарантия «настройки не сбрасываются».
- UI **читает** текущее состояние и преднаполняет форму: новая подкоманда
  `yandex-disk get-config` (см. §4) возвращает `dir`, `remote`, `clean_thumbs`,
  `interval` (если есть) и **флаг** «токен настроен» (по наличию секции
  `[yandexdisk]` в `rclone.conf`) — **без значения токена**.
- **Обратная совместимость формата.** Старый `config.cfg` (только `dir`+`remote`,
  без новых ключей) обязан читаться без ошибок — парсер `cfg()` это уже умеет
  (отсутствующий ключ → пустая строка). Это фиксируется отдельным герметичным
  тестом (§8), как ранее зафиксирована совместимость 3-полевого `sync.state`.

## 4. Архитектура: тонкий CGI → подкоманды обёртки → helpers в common.sh

Принцип канона: общие пути/парсер/формат — только в `common.sh`; логика — в
обёртке, не размазана по CGI. Поэтому **вся** запись/чтение конфигов делегируется
обёртке `yandex-disk`, а новый CGI остаётся тонким парсером HTTP.

**Новые подкоманды `yandex-disk` (контракт расширяется обратносовместимо):**

| Подкоманда | Назначение | Безопасность |
|---|---|---|
| `set-folder <dir> [remote] [clean_thumbs]` | Валидирует и атомарно пишет `config.cfg` | Валидация §3.4 |
| `set-token` (JSON со stdin) | Валидирует JSON и пишет `rclone.conf` (`0600`) | Токен со stdin, не argv; не логируется |
| `get-config` | Печатает текущий конфиг в машиночитаемом виде (`key=value`/JSON) | **Без** значения токена, только флаг «настроен» |
| `check-folder <dir>` | Сообщает: существует / доступна на запись / владелец | Для подсказки про права (§1) |

Помощники записи/валидации (`write_cfg_atomic`, `cfg_set`, `validate_dir`,
`validate_remote`, `is_token_configured`) живут в `common.sh` — единый источник
истины, переиспользуются обёрткой и покрываются герметикой.

**Новый CGI `settings.cgi`** (вкладка `settings`):
- `GET` → вызывает `yandex-disk get-config`, отдаёт состояние формы (JSON);
- `POST` → парсит поля, вызывает соответствующую подкоманду (`set-folder` /
  `set-token` / `sync`), возвращает результат/ошибку. **CSRF/доступ:** запрос
  обязан быть в аутентифицированной админ-сессии DSM (webman за DSM-логином);
  для мутаций проверять `SynoToken`/использовать `authenticate.cgi`-паттерн.

В **ветке B** (§3.1) между CGI и записью добавляется привилегированный посредник,
но контракт подкоманд и тесты не меняются.

**UI (`spk/package/ui/main.js`).** Добавить вкладку **«Настройки»** (ключ
`settings` = имя CGI — контракт канона) с формой: поля папки/remote/clean_thumbs,
блок подключения Яндекса (Tier 1/2), кнопки «Сохранить», «Подключить»,
«Синхронизировать сейчас», блок расписания (по §3.3). При открытии — `GET` для

## 8. Тесты и Definition of Done

**Обязательная цепочка (после каждой нетривиальной правки):**

```bash
bash build.sh && bash test/run-hermetic.sh && sh test/check-coverage.sh && bash test/check-reproducible.sh
```

Мутационный гейт `sh test/mutate.sh` (порог `YD_MUT_MIN`) — перед сдачей значимой
правки ядра/ночью; новая логика должна быть покрыта так, чтобы score ≥ порога.

**Новые герметичные сценарии `test/run-hermetic.sh`** (стиль `Tnn`, через
`fake-rclone` + `YD_*`-оверрайды; правка `test/` — отдельный PR/коммит):

- `set-folder`: пишет `config.cfg` с `dir`/`remote`/`clean_thumbs`; атомарность;
- `set-folder` отвергает невалидный ввод (относительный путь, перевод строки,
  путь с ` #`, инъекцию);
- `set-token`: пишет `rclone.conf` с секцией `[yandexdisk]`, права `0600`,
  **токен отсутствует в stdout**; отвергает не-JSON / JSON без `access_token`;
- `get-config`: возвращает `dir`/`remote`/`clean_thumbs` + флаг «токен настроен»;
  **значение токена отсутствует** в выводе (assert по подстроке);
- **обратная совместимость**: `get-config` на старом `config.cfg` (только
  `dir`+`remote`) — корректный вывод, без ошибок;
- `check-folder`: существует/доступна/нет;
- CGI-тест `settings.cgi` (Phase 2): `GET` → JSON состояния; `POST` →
  делегирование в обёртку (через подменённую обёртку/`fake-rclone`);
- **golden**: при необходимости снимок человекочитаемого вывода новых подкоманд;
  существующие `status-configured/unconfigured` и `state-line-*` **не меняются**.

**Mutation-sanity** каждого нового сценария: внести минимальную поломку
поведения, показать падение теста, откатить (§3.2 `ai-workflow.md`).

**Только на NAS (вне герметичной цепочки, ручная валидация перед релизом):**
euid/права CGI (Phase 0); реальная валидность токена и `rclone.conf`; видимость
вкладки и работа формы в DSM; (Tier 2) реальный OAuth-redirect; (Опция B/C)
расписание. Эти пункты — кандидаты в `test-on-nas-functional.sh`.

## 12. Риски и митигации

| Риск | Митигация |
|---|---|
| CGI не имеет прав писать конфиги (ветка B) | Phase 0-спайк до реализации; привилегированный посредник по §3.1 |
| Утечка токена (argv/лог/ответ) | Токен со stdin, прямой INI `0600`, явные assert-тесты «токена нет в выводе» (§6, §8) |
| Порча `config.cfg` инъекцией/` #` в пути | Жёсткая валидация + атомарная запись (§3.4) |
| Регресс существующих контрактов | Полная герметика + неизменные golden; правки `test/` отдельным PR |
| «Настройки сбросились» после обновления | Опираемся на уже рабочие pre/postupgrade; тест обратной совместимости `get-config` (§3.5, §8) |
| Невоспроизводимая сборка из-за CRLF в новых файлах | `.gitattributes` `eol=lf` для `settings.cgi`; CRLF-гейт `build.sh` |
| Размывание инварианта «нет демона» (Опция B) | По умолчанию Опция A; B/C — только с одобрением человека |
