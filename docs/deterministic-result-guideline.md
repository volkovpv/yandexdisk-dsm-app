## 0. Что значит «детерминированный результат» здесь

LLM по своей природе **стохастична**: один и тот же промпт может дать разный текст,
даже при `temperature=0`. Поэтому «детерминированный результат» здесь — это **не**
«модель всегда печатает одни и те же символы», а:

> **Сходимость итогового артефакта к спецификации, которую можно проверить машиной,
> вне зависимости от того, каким стохастическим путём агент к ней пришёл.**

Ключевая величина — **покрытие гейтами**: доля понятия «правильно», которую можно
выразить исполняемой проверкой (pass/fail). Чем оно выше, тем детерминированнее
результат и тем меньше нужен человек в цикле на рутинных шагах.

Два принципа, на которых держится весь документ:

1. **Детерминизм даёт гейт, а не модель.** Замена Claude на YandexGPT почти не меняет
   детерминированность результата — её определяет то, что после генерации прогоняется
   как объективная проверка. Слабее модель — больше итераций до зелёного, но при
   полном покрытии гейтами финал тот же.
2. **Нельзя «глушить» гейт ради прохождения.** Отключить проверку, ослабить правило,
   замокать падающий тест «чтобы прошло» — значит уменьшить покрытие гейтами, то есть
   уменьшить детерминизм. Это запрещено (см. §3).

## 1. Детерминированный субстрат проекта

Здесь нет компилятора и графа зависимостей (как в типизированных сервисах), но
фундамент машинной проверяемости заложен и **уже внедрён в полном составе**.

### 1.1. `build.sh` как fitness-pipeline

Единственная команда `bash build.sh` прогоняет всю off-device проверку и собирает
пакет:

| Проверка | Что ловит | Реализация |
|---|---|---|
| Синтаксис shell | сломанный POSIX-sh в любом скрипте | `dash -n` по списку `POSIX_SH` |
| Стиль/баги shell | типовые ошибки оболочки | `shellcheck -S warning` (hard-fail) |
| Переносимость | bash-измы, которые `dash -n` пропускает | `checkbashisms` |
| CRLF-гейт | скрытый CRLF в скриптах пакета | проверка `\r` по `$POSIX_SH` |
| Валидность control-файлов | битый `spk/conf/privilege` | `python3 -c 'json.load(...)'` |
| Целостность движка | подменённый/неполный `rclone` | SHA256 zip **и** бинарника |
| Архитектура движка | бинарник не той арх. для профиля | ELF `e_machine` 183=arm64 / 62=amd64 по `YD_ARCH` (hard-fail) |
| Контракт маркеров | бамп rclone сломал счётчики | `test/check-rclone-contract.sh` |
| Дрейф версий | рассинхрон версии в доках/конфигах | `test/check-version-drift.sh` |
| Сборка пакета | пакет не собирается/кривой `.spk` | реассембляция `package.tgz` + `.spk` |

Зафиксированы локаль/время/umask (`LC_ALL=C LANG=C TZ=UTC`, `umask 022`) и
`SOURCE_DATE_EPOCH` — среда сборки герметична, «skip-дыр» (информационных пропусков
без установленного инструмента) больше нет.

### 1.2. Воспроизводимая сборка (байт-в-байт)

`build.sh` собирает архивы детерминированно: `tar --sort=name`,
`--mtime="@${SOURCE_DATE_EPOCH}"`, `--owner=0 --group=0 --numeric-owner`, `gzip -n`.
Результат — **один и тот же SHA256 при каждой чистой пересборке**. Самопроверка —
`test/check-reproducible.sh` (rebuild-twice-and-compare). **Любая правка `build.sh`,
ломающая воспроизводимость, недопустима** (см. §2.7).

### 1.3. Герметичный поведенческий тест без NAS

Главный разрыв («синхронизация реально работает» проверялась только на живом NAS)
закрыт: `test/run-hermetic.sh` + `test/fake-rclone` прогоняют машину состояний sync,
счётчики, ротацию, авто-`--resync`, single-run guard во временном `YD_*`-окружении.
Golden-снимки наблюдаемого контракта — в `test/golden/`. Подробности — §4.

### 1.4. CI как принудительный гейт

`.github/workflows/build-spk.yml` гоняет всю цепочку гейтов на каждый push/PR любой
ветки; публикация версионного `.spk` — на push в `main`. То есть гейты исполняются не
«по доброй воле», а на каждом изменении.

### 1.5. Что остаётся за NAS

Финальная функциональная валидация против реального аккаунта Яндекса —
`test-on-nas-functional.sh`, `test-on-nas-install.sh`. Это негерметичный гейт с
человеком и живыми кредами; он **дополняет** герметичный, но не заменяет его.

## 2. Канон проекта (правила, обязательные для агента)

> Канонический и обязательный минимум этих правил продублирован в корневом
> [`../CLAUDE.md`](../CLAUDE.md) — он единственный источник истины для агента.
> Ниже — развёрнутое обоснование.

### 2.1. Только POSIX-sh; bash — под запретом в пакете

Все скрипты пакета — `#!/bin/sh` и обязаны проходить `dash -n`. Никаких bash-измов
(`[[ ]]`, массивы, `local` без объявления, `function name()`): на DSM `sh` — не bash.
Исключение — внешние утилиты разработчика (`build.sh`, `test-on-nas-*.sh`). Новый
sh-скрипт → сразу добавить в `POSIX_SH` в `build.sh`. Принудительно исполняется
`dash -n` + `checkbashisms`.

### 2.2. `common.sh` — единственный источник истины

Пути, парсер `config.cfg` (`cfg`), ротация логов (`rotate_log`), формат строки статуса
(`sync_state_line`), `_now` живут **только** в `spk/package/common.sh` и подключаются
через `. "$.../common.sh"`. Копипастить путь или формат в `yandex-disk`,
`yandex-logger`, `start-stop-status`, CGI запрещено.

### 2.3. Нет резидентного демона

Архитектурный инвариант: на DSM 7 фоновый shell-цикл ненадёжен. Периодическую
синхронизацию делает DSM Task Scheduler (`yandex-disk sync`), а `start-stop-status`
поднимает только лёгкий heartbeat `yandex-logger`. Нельзя «вернуть» демон/`while true`.

### 2.4. Контракты, которые нельзя ломать молча

Изменение требует синхронной правки всех потребителей, обновления герметичных
тестов/golden в том же коммите и явного одобрения человека:

- **Маркеры лога rclone** (`count_run_transfers`): `Queue copy to Path2` (*отправлено*),
  `Queue copy to Path1` (*получено*), `Copied (replaced existing)` (*изменено*),
  `Queue delete` (*удалено*). Триггер авто-восстановления: `cannot find prior` /
  `Must run --resync`. Заголовок прогона: `===== sync started ...`. При бампе движка
  перепроверить, что подстроки присутствуют (`test/check-rclone-contract.sh`).
- **Формат `sync.state`** — ровно 7 полей через `|`:
  `status|timestamp|result|sent|received|modified|deleted`. Старый 3-полевой формат
  должен оставаться читаемым (обратная совместимость заложена).
- **Имена UI-вкладок** в `main.js` (`status`/`log`/`sync_log`) = имена CGI-эндпоинтов.
  Менять можно человекочитаемые подписи, **не ключи**.
- **Имя remote `yandexdisk`** ожидается обёрткой и описано в `INFO`.

### 2.5. Версия бьётся синхронно

Любой релиз меняет версию одновременно в `spk/INFO`, `CHANGELOG-ARM.md`,
`RELEASE-INFO-ARM.txt` (SemVer `МАЖОР.МИНОР.ПАТЧ`). Рассинхрон ловит
`test/check-version-drift.sh`.

### 2.6. Security-инварианты — не ослаблять

- Пакет работает под `sc-yandexdisk` (`run-as: package`) — не поднимать до root.
- **OAuth-токен, `rclone.conf`, любые секреты — никогда в коде, git и логах.**
- Не логировать ПДн/токены. Запрос «убери проверку/exclude, чтобы прошло» — отказать,
  объяснить первопричину, поднять как риск.
- `--exclude`-список в `_bisync` (`#recycle`, `@eaDir`, `#snapshot`, `@tmp`, `.DS_Store`,
  `Thumbs.db`) не урезать молча.

### 2.7. Воспроизводимость сборки — священна

Флаги детерминизма (`--sort`, `--mtime`, `--numeric-owner`, `gzip -n`) и пиннинг
`RCLONE_VERSION` + обе SHA256 — часть контракта §1.2. Менять только осознанно, с
одновременным обновлением ожидаемых сумм.

### 2.8. Среда исполнения

Только Linux-инструменты и POSIX-пути; никаких PowerShell/`C:\`. Команды — в
неинтерактивном режиме, безопасные операции (build/test) выполнять сразу, цепляя `&&`.

## 3. Обязательный пост-таск гейт

После **любой** нетривиальной задачи прогнать и довести до зелёного:

```bash
bash build.sh                 # синтаксис sh + shellcheck + checkbashisms + CRLF + JSON + ELF + контракты + воспроизводимая сборка
bash test/run-hermetic.sh     # фейк-rclone + проверка машины состояний без NAS
bash test/check-reproducible.sh   # rebuild-twice-and-compare
```

Если шаг падает — **починить первопричину в коде** и перезапустить цепочку **с
начала**. Задача не выполнена, пока всё не зелёное. **Нельзя глушить
проверку/тест/правило** (§0). На реальном NAS — финальная ручная валидация перед
релизом, но она не заменяет герметичный гейт.

> Правки `build.sh`, `test/`, `.github/workflows/` — **отдельным PR**, не вместе с
> кодом, который они проверяют (защищённый периметр гейтов, §11.6).

## 4. Герметичный поведенческий тест без NAS (как устроен)

### 4.1. Почему это возможно «из коробки»

Код спроектирован под подмену окружения: каждый путь уважает `YD_*`-оверрайды —
`YD_PKG_DIR`, `YD_HOME`, `YD_VAR`, `YD_RCLONE_CONF`, `YD_LOG_MAX_BYTES`,
`YD_LOG_INTERVAL`. Весь пакет можно запустить во временном каталоге, не трогая
`/var/packages`. Единственная внешняя зависимость — бинарник `rclone` — подменяется
через переменную `RCLONE` (`RCLONE="${RCLONE:-$SELF_DIR/rclone}"`).

### 4.2. `test/fake-rclone` (resync-aware)

Шим эмулирует ровно то, что вызывает обёртка: `version`, `bisync ... --log-file <f>`
(с опциональным `--resync`) и passthrough. На `bisync` дописывает в `--log-file`
маркеры из §2.4. Поведение задаётся окружением:

```
FAKE_RC          — exit-код ИНКРЕМЕНТАЛЬНОГО bisync (без --resync); по умолчанию 0
FAKE_RESYNC_RC   — exit-код bisync --resync; по умолчанию 0
FAKE_SENT / FAKE_RECV / FAKE_MOD / FAKE_DEL — сколько маркеров дописать в --log-file
FAKE_NEED_RESYNC=1 — дописать триггер recovery (только в инкрементальном прогоне)
FAKE_ARGS_FILE   — если задан, сохранить туда аргументы bisync (для контракт-теста CLI)
```

Отдельные коды возврата для инкрементального и resync-вызова критичны: иначе
восстановительный `_bisync --resync` унаследует `FAKE_RC=1` и сценарий авто-recover
ложно упадёт.

### 4.3. Сценарии `test/run-hermetic.sh`

Каркас: `#!/bin/sh`, `set -eu`, проходит `dash -n`, в `POSIX_SH`; изоляция через
`WORK=$(mktemp -d)` + `trap`; помощники без `eval`. Реестр сценариев (`f4` = поле 4
`sync.state` и т.д.; `$YD` = `spk/package/yandex-disk`):

| # | Сценарий | Точное ожидание |
|---|---|---|
| T1 | Первый прогон ⇒ `--resync`, baseline | exit 0; `f1=idle f3=ok f4=2 f5=1`; есть `.bisync_resynced`; в логе `===== sync started ` |
| T2 | Окно счётчиков = только последний прогон | `f4=0 f5=0 f6=3 f7=1` (маркеры T1 не пересчитаны) |
| T3 | Падение без триггера | rc=7; `f1=error f3=rc=7` |
| T4 | Авто-recover успешный | exit 0; `f1=idle f3=ok`; в stdout `[auto-recover]` |
| T5 | Авто-recover неуспешный | exit 1; `f1=error f3=rc=1` |
| T6 | Single-run guard (`flock`) | stdout `sync already running, skip`; в логе `===== sync skipped ` |
| T7 | Ротация лога | существует `rclone.log.1` |
| T8 | Не сконфигурирован | rc=1; stdout `not configured` |
| T9 | `resolve_remote`: единственный чужой remote | вывод содержит `mydisk:` |
| T10 | Парсер `cfg`: таблица входов | кавычки/комментарии/регистр/пустой ключ |
| T11 | `sync_state_line`: 3-полевой формат | 1 строка; нет `Файлы —` |
| T12 | `sync_state_line`: 7-полевой формат | 2 строки; `отправлено): 2`, `получено): 1` |
| T13 | Контракт CLI-флагов `_bisync` | присутствуют `--conflict-resolve`, `path1`, `--inplace`, `--max-lock` и все 6 exclude-масок (`grep -qxF -- ...`) |
| T14 | (опц.) `yandex-logger` пишет историю | `status_history.log` содержит текущий статус |

### 4.4. Куда класть и как включить в CI

Скрипты — в `test/`, добавлены в `POSIX_SH`; шаг `bash test/run-hermetic.sh` —
в `build-spk.yml` перед сборкой `.spk`, так гейт принудителен.

## 5. Контракт-тесты наблюдаемого поведения

- **Golden-снимки** человекочитаемого вывода (`status`, `sync_state_line` для 7- и
  3-полевого формата) в `test/golden/`; сравнение через `diff -u` после нормализации
  temp-путей и таймстемпов. Правка текста без обновления эталона → красный.
- **Контракт маркеров rclone в бинаре** — `test/check-rclone-contract.sh`:
  `grep -qaF "<маркер>" spk/package/rclone` по 4 маркерам + 2 триггерам recovery
  (именно `grep -a`, без зависимости от `strings`/binutils).
- **Table-driven тесты парсеров** `cfg()` и `count_run_transfers`: пары
  «вход → ожидаемый выход» (комментарии, пробелы, кавычки, пустые значения, CRLF).

## 6. AI-движок: как использовать (в т.ч. YandexGPT) детерминированно

- **Разделяйте «модель» и «харнесс».** Модель — LLM, генерирующая диффы; харнесс —
  агентский цикл «читать → bash → править → гонять гейты → итерировать». Для этого
  проекта поверхность маленькая (POSIX-sh + чуть JS), домен узкий, есть жёсткий гейт,
  документация на русском — YandexGPT годится как генератор; agentic-надёжность
  проверяйте собственным eval’ом перед автономными петлями.
- **Настройки на повторяемость:** `temperature` 0–0.3, низкий `top_p`, **фиксированная
  версия модели** в конфиге (не «latest»).
- **YandexGPT через OpenAI-совместимый API:** `base_url` на эндпоинт Yandex, модель
  `yandexgpt`, гейтом — `bash build.sh` + `bash test/run-hermetic.sh`. Креды — только из
  окружения/Lockbox, никогда в коде или промптах в git.
- **Главный вывод:** выбор модели почти не влияет на детерминированность результата —
  влияют покрытие гейтами (§1, §4) и соблюдение канона (§2).

## 7. Чек-лист агента перед сдачей задачи

- [ ] Все скрипты пакета — POSIX-sh, проходят `dash -n`; новые добавлены в `POSIX_SH`.
- [ ] Общие пути/форматы взяты из `common.sh`, не скопированы (§2.2).
- [ ] Контракты не сломаны молча: log-маркеры, 7-полевой `sync.state`, ключи UI/CGI,
      имя remote `yandexdisk` (§2.4).
- [ ] Нет возврата резидентного демона (§2.3).
- [ ] Security: нет токенов/секретов/ПДн в коде, git и логах; `run-as` не повышен;
      `--exclude`-список цел (§2.6).
- [ ] Версия синхронна в `INFO` + `CHANGELOG-ARM.md` + `RELEASE-INFO-ARM.txt` (если релиз).
- [ ] Воспроизводимость сборки не нарушена; при бампе rclone обновлены обе SHA256 (§2.7).
- [ ] Зелёные: `bash build.sh`, `bash test/run-hermetic.sh`, `bash test/check-reproducible.sh`.

## 8. Эффективные промпты для этого репозитория

1. **Привязывайте к гейту:** «доведи до зелёного `bash build.sh` и
   `bash test/run-hermetic.sh`, чини первопричину, не глуши проверки».
2. **Называйте контракт:** «не меняй log-маркеры rclone и 7-полевой формат `sync.state`».
3. **Очерчивайте периметр:** «правки только в `spk/package/yandex-disk` и `common.sh`,
   `build.sh` не трогай».
4. **Для нового поведения требуйте тест:** «добавь ветку и **герметичный тест** на неё в
   `test/run-hermetic.sh`».

## 9. Когда останавливаться и спрашивать

Агент уточняет у человека (а не угадывает), если задача требует: ослабить
security-инвариант (§2.6); сменить версию rclone (новые SHA + перепроверка log-маркеров);
вернуть резидентный демон; изменить контракт (`sync.state`, log-маркеры, ключи UI/CGI,
имя remote); поменять флаги воспроизводимости; внести изменение, проверяемое только на
NAS и непокрываемое герметичным тестом.

## 10. Краткий вывод

Проект несёт **детерминированный субстрат**: воспроизводимая байт-в-байт сборка,
тотальные статические гейты, герметичный поведенческий тест и контракт-тесты,
принудительно прогоняемые в CI. Детерминизм результата обеспечивают **гейты и канон**,
а не марка модели: любой агент получает быстрый объективный сигнал на каждом шаге.

## 11. Углублённое усиление детерминизма (оси A–F)

Приёмы сгруппированы по осям: **(A)** герметичность среды, **(B)** тотальность гейтов,
**(C)** фиксация поведения, **(D)** рефакторинг/создание фич, **(E)** детерминизм самого
агента, **(F)** supply-chain.

### 11.1. Ось A — герметичность сборки
Зафиксированы `LC_ALL=C/LANG=C/TZ=UTC`, `umask 022`, `SOURCE_DATE_EPOCH` (**внедрено**);
самопроверка воспроизводимости `test/check-reproducible.sh` (**внедрено**). Следующий
шаг (☐) — сборка в запиненном по digest контейнере, чтобы версии
`tar`/`gzip`/`dash`/`shellcheck` были одинаковы у всех.

### 11.2. Ось B — тотальность гейтов
Закрыты «skip-дыры»: отсутствие `shellcheck`/`python3` → `exit 1`; `shellcheck` hard-fail
(`-S warning`); ELF-проверка `e_machine != 183` → отказ; добавлен `checkbashisms` и
CRLF-гейт (**внедрено**).

### 11.3. Ось C — фиксация поведения
Герметичный тест §4 + golden-снимки §5 + контракт-тест маркеров (**внедрено**).
Table-driven тесты парсеров — частично (T10).

### 11.4. Ось D₁ — рефакторинг старых фич
Characterization-first: перед правкой снять golden/герметичные тесты на текущее
поведение; вести рефакторинг **под зелёным**; «зубастость гейтов» (mutation-sanity, §13)
— периодически вносить поломку и убеждаться, что гейт её ловит; strangler для крупных
переписываний.

### 11.5. Ось D₂ — новые фичи
Скаффолд/шаблоны для типовых расширений (новая подкоманда `case`, CGI+вкладка, поле
`sync.state`); Definition of Done = новый герметичный тест (+ golden при смене вывода);
контракт раньше реализации.

### 11.6. Ось E — детерминизм агента
Plan-freeze (план → апрув → исполнение в периметре); proposer/checker (независимый
ревьюер против чек-листа §7); политика как код (`CLAUDE.md`, запиненные
модель/temperature); **гейты — защищённый периметр**: правка `build.sh`, `test/`,
`.github/workflows/` — отдельным PR; re-run convergence как диагностика
недоопределённости спецификации.

### 11.7. Ось F — supply-chain
Запинить GitHub Actions по SHA, а не по тегу (**внедрено** в W6); единый источник версии
rclone + drift-гейт `test/check-version-drift.sh` (**внедрено**). Перспектива (☐): SBOM и
provenance/подпись `.spk`, externalize deps-lock (`URL+SHA` внешних входов).

### 13.3. Mutation-sanity: диверсии, которые гейты обязаны ловить

Каждая диверсия вносится временно, гейт запускается, фиксируется **красный**, диверсия
откатывается. Гейт, не упавший на своей диверсии, чинится (а не таблица).

| # | Диверсия | Обязан упасть |
|---|---|---|
| 1 | `Queue copy to Path2` → `…PathX` в `count_run_transfers` | `run-hermetic` T1 (`f4=0`) |
| 2 | Убрать поле из `printf` в `write_sync_state` | `run-hermetic` T1/T12, golden |
| 3 | Вставить `[[ -n "$LOCAL" ]]` в `yandex-disk` | `dash -n` / `checkbashisms` |
| 4 | Заменить `--mtime` на текущее время в `build.sh` | `check-reproducible` |
| 5 | Удалить `--exclude "@eaDir/**"` из `_bisync` | `run-hermetic` T13 |
| 6 | Подложить бинарь не той арх. (`e_machine` ≠ профиль `YD_ARCH`) | ELF-гейт `build.sh` (exit 1) |
