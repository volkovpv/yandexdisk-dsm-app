# Proposal: самопроверка пакета при установке + план отказа/отката

Статус: **на согласование** (требует явного одобрения — затрагивает контракт пакета
и lifecycle; по CLAUDE.md «Остановись и спроси человека»).
Автор черновика: AI-сессия. Дата: 2026-06-25.

---

## 1. Что просили

1. Чтобы при обычной установке `.spk` пакет **сам, незаметно для пользователя**,
   проводил проверки на NAS, **подробно логировал** результат и: всё хорошо →
   установка идёт как обычно; что-то не так → честно отказывается.
2. **План отказа/отката.** Если проверки (`preinst`/`postinst`) не прошли —
   установку не выполнять и откатиться к предыдущей версии. На FAIL: показать
   человеку подробный лог, предложить создать issue на GitHub с этим логом и
   предложить откатиться до предыдущей версии.

Источник идеи — ручные `test-on-nas-install.sh` / `test-on-nas-functional.sh`,
которые сейчас гоняются по SSH **после** установки (см. `docs/ai-workflow.md` §1).

## 2. Вывод (TL;DR)

| Часть идеи | Вердикт |
|---|---|
| Незаметная **самопроверка установки** (структура, arch rclone, пользователь, каталоги), лог, отказ при провале | **Реализуемо** — POSIX-`postinst` (+ `preinst` для предусловий). |
| **Функциональный тест синхронизации** во время установки | **Нереализуемо** (нет токена до настройки, повесит установку, нужна сеть). Остаётся ручным/UI-шагом после настройки. |
| «Тесты упали → DSM сам откатит к предыдущей версии» | **Так DSM НЕ умеет** (нет транзакционного апгрейда с автооткатом, §3). Защитить старую версию может только ранний `preinst`; payload-проверки `postinst` до неё «не дотягиваются». |
| **Авто-создать GitHub issue** с логом из install-скрипта | **Нельзя** (нет авторизации/сети/прав, запрет наружу без подтверждения, риск утечки в публичный issue). Реалистично — санитизированный лог + **пред-заполненная ссылка** `issues/new`. |
| «Откат к предыдущей версии» на сбойном апгрейде | Не пакетная авто-операция, а **ручная переустановка прежнего `.spk`**; данные при этом уже сохранены `preupgrade` (§3, §5). |

Иными словами: «нажал Установить → пакет сам себя проверил → либо чисто встал,
либо честно отказал, не поломав то, что работало» — **достижимо**, но через
**асимметричную модель гейтов** (§4) и **честный план отказа** (§5), а не через
несуществующий автооткат DSM.

## 3. Критично: как DSM реально ведёт себя при install / upgrade / fail

Это фундамент всего плана. Поведение отмеченное **⚠ ВЕРИФ** — обязательно
подтвердить на реальном NAS до кода (§12); ниже — рабочая модель.

### 3.1. Lifecycle-скрипты и точки невозврата
Порядок (упрощённо): `preinst` → **распаковка файлов** → `postinst` → start.
Для апгрейда добавляются `preupgrade` (до) и `postupgrade` (после), а старые файлы
**заменяются** между ними. **Точка невозврата — распаковка**: всё, что до неё
(`preinst`, `preupgrade`), может безопасно прервать установку; всё, что после
(`postinst`), уже работает по «новой» раскладке.

### 3.2. Что значит «провал» на каждом этапе
- **`preinst` != 0** → DSM прерывает установку **до распаковки**. Свежая
  установка: пакета нет, система чистая. Апгрейд: **старая версия должна остаться
  целой** (⚠ ВЕРИФ: точный порядок относительно остановки/снятия старой версии —
  главный неизвестный фактор).
- **`postinst` != 0** → DSM помечает установку неуспешной. Свежая установка:
  ожидаем, что DSM уберёт полу-распаковку (⚠ ВЕРИФ). Апгрейд: новые файлы **уже
  легли поверх старых** — штатно «вернуть старую версию» DSM **не умеет** (см. 3.3).

### 3.3. Нет транзакционного апгрейда с автооткатом
У DSM **нет** примитива «постинст упал → восстанови предыдущую версию». После
подмены файлов поздний провал оставляет пакет в новой (возможно битой) раскладке,
а не откатывает. Поэтому:
- «Откат к предыдущей версии» **не может** инициировать пакет после распаковки.
- Реальный откат на сбойном апгрейде = пользователь **вручную ставит прежний
  `.spk`** (наши релизы на GitHub Releases). Наша задача — сделать это лёгким и
  безопасным, а **данные** при этом уже спасены `preupgrade` (§5.4).

### 3.4. `preinst` не видит новый payload
На момент `preinst` файлы **не распакованы** — проверить arch rclone / работу
обёртки нельзя. `preinst` проверяет **только окружение** (место, пользователь,
каталоги, опц. короткий сетевой пинг). Это и есть причина асимметрии §4.

### 3.5. Что DSM показывает человеку при провале
Package Center выводит обобщённую ошибку + (часто усечённые) последние строки
stderr сбойного скрипта (⚠ ВЕРИФ что именно и сколько). Богатого диалога с
кнопками из shell-скрипта **не будет** — отсюда дизайн вывода в §5.2.

### 3.6. Полезные факты из репозитория
- `preupgrade`/`postupgrade` **уже** сохраняют и restore-if-missing **данные**
  пользователя (токен, `config.cfg`, `sync.state`, bisync-DB) через
  `SYNOPKG_TEMP_UPGRADE_FOLDER`. План отката **опирается** на это, не дублирует.
- Задачу синхронизации в Планировщике DSM создаёт **сам пользователь** (INFO,
  шаг 5), не пакет → сбойная установка не оставляет пакетную задачу-мину. Но на
  **апгрейде** уже существующая пользовательская задача продолжит дёргать
  `/usr/local/bin/yandex-disk` (возможно битый) до переустановки — аргумент за
  STRICT `preinst` (§4.2).
- Корректно собранный `.spk` arch-проверку `postinst` в норме **не проваливает**:
  arch гарантируется `arch=` в INFO + герметичными гейтами + marker-контрактом
  rclone. Значит `postinst` — это **дешёвая страховка** от порчи при загрузке/
  распаковке, а не частый сценарий → это снижает ставки и оправдывает ADVISORY
  (§4.3), а не сложный движок отката (§7).

## 4. Дизайн: асимметричная модель гейтов

Главный вывод §3: **защитить рабочую старую версию может только `preinst`** (до
точки невозврата). `postinst` срабатывает уже поздно. Поэтому роли разные.

### 4.1. Карта проверок (из `test-on-nas-install.sh`)

Принцип размещения: `preinst` видит **только окружение до распаковки** (§3.4) и
**до создания пользователя пакета** (см. ниже) — поверхность проверок тонкая.
Всё, что зависит от payload или от `sc-yandexdisk`, может проверяться **только в
`postinst`**.

| # | Проверка | Где | Примечание |
|---|---|---|---|
| Env | свободное место на томе установки | `preinst` | до распаковки; безопасный abort. Каталогов пакета ещё нет — проверяем том, не `$VAR_DIR`. |
| Env | (опц.) короткий пинг до Яндекса, таймаут ≤3с | `preinst` | мягко, не блокировать жёстко; см. §4.2. |
| User | пользователь `sc-yandexdisk` существует | `postinst` | **НЕ `preinst`**: на первой установке его создаёт сам DSM в ходе установки (до `postinst`), в `preinst` его ещё нет — проверка там провалила бы каждую первую установку. Здесь — валидирует, что user-setup DSM отработал. ⚠ ВЕРИФ момент создания (§12). |
| Bin | rclone присутствует и его arch **совпадает с arch хоста** (ELF `e_machine` бинаря == ожидаемое из `uname -m`: 183=arm64 / 62=x86-64) | `postinst` | payload есть только после распаковки. **Arch-agnostic** (§10-8): один `spk/scripts/` пакуется в **оба** `.spk` (ARM и x86_64, см. `build.sh:230-231` — патчится только `arch=`/`displayname=`, `package="YandexDisk"` общий), поэтому жёсткий aarch64/183 завалил бы **каждую** x86_64-установку. Сверяемся с хостом, как делает `build.sh:188-192`. |
| Bin | обёртка `yandex-disk version` (e2e-смоук) | `postinst` | «обёртка» = `spk/package/yandex-disk` (POSIX-sh wrapper над rclone; её `version` зовёт `rclone version` → строка с arch, **не привязываемся к `arm64`** — см. arch-agnostic выше). Одним вызовом: скрипт запускается, подсосал `common.sh`, нашёл рабочий rclone под текущую арку. Зависит от `sc-yandexdisk` → только `postinst`. Запуск «под `sc-yandexdisk`» или напрямую — зависит от того, под кем бежит `postinst` (⚠ ВЕРИФ §12; если уже `sc-yandexdisk` — без `sudo`, ср. память про CGI). |
| Struct | каталог конфига существует | `postinst` | структура раскладки. |
| — | `config.cfg`/`rclone.conf` существуют, remote настроен | **нет** | их нет на свежей установке (настройка — потом, в UI). Не провал. |
| — | `synopkg status running` | **нет** | install ещё идёт, статус не «running». |

### 4.2. `preinst` — STRICT (жёсткий гейт окружения)
Срабатывает до разрушения → abort **безопасен** (старая версия цела). Проверяет
только окружение (см. таблицу). FAIL → ненулевой выход, установка не начинается.
Сетевой пинг — **опционально и мягко** (короткий таймаут; недоступность сети не
должна валить установку рабочего пакета — токен и так заводится позже).
На свежей установке `$VAR_DIR` ещё не существует → `preinst` персистентный лог
**не ведёт**; при FAIL печатает причину только в stderr (её показывает Package
Center, §5.2).

### 4.3. `postinst` — ADVISORY по умолчанию (громкая страховка)
Срабатывает после распаковки → откатить старую версию штатно нельзя. Поэтому:
- проверяет, что payload лёг корректно (arch/обёртка/структура), **без сети,
  без `setsid`/bisync** (установка не должна блокироваться — память
  «CGI must not block on long ops»);
- **FAIL на свежей установке** → ненулевой выход (DSM пометит установку
  неуспешной — это и есть желаемый «чистый отказ»; ⚠ ВЕРИФ что DSM уберёт
  полу-распаковку);
- **FAIL на апгрейде** → старая версия уже заменена; жёсткий выход не вернёт её.
  Поведение определяется **точкой согласования §10-1** (ADVISORY: пакет
  «установлен», но сам знает что битый, кричит в статус/лог + инструкция отката;
  vs STRICT: видимый failed-статус + та же инструкция). Рекомендация — ADVISORY,
  пока на железе не подтверждено поведение DSM.

### 4.4. Требования к скриптам (канон)
`#!/bin/sh`; проходят `dash -n`, shellcheck `-S warning`, checkbashisms; пути —
**только** из `spk/package/common.sh` (source / `YD_*`), значения не копировать;
лог — через `LOG_DIR`/`rotate_log`; `mkdir -p "$LOG_DIR"` перед записью (как
`postupgrade` делает `mkdir -p "$VAR_DIR"`).

**Оговорка для `preinst` (R5):** на момент `preinst` payload **ещё не распакован**
(§3.4) → `spk/package/common.sh` физически отсутствует, `. common.sh` невозможен.
Поэтому требование «пути только из `common.sh`» относится к `postinst` (после
распаковки `common.sh` лежит в `target/`). `preinst` контрактные значения **не
копирует**, а оперирует только тем, что даёт сам DSM: том установки берёт из
`SYNOPKG_*` (точные имена — ⚠ ВЕРИФ §12-6), и не пишет персистентный лог (§4.2).

### 4.5. Что НЕ трогаем
`test-on-nas-functional.sh` остаётся ручным инструментом разработчика — в
install-гейт его превратить нельзя (§9).

## 5. План отказа и отката (ядро задачи)

Обработчик FAIL общий для `preinst`/`postinst`, но **ветвится по сценарию**
(свежая установка vs апгрейд).

**Детект сценария — кросс-сигнальный (R3, решено §10-10).** Не полагаемся на одну
переменную: вся асимметрия STRICT/ADVISORY висела бы на `SYNOPKG_OLD_PKGVER`, чьё
имя/наличие — ⚠ ВЕРИФ (§12-6). Комбинируем несколько признаков: `SYNOPKG_OLD_PKGVER`
(если есть) **И** наличие `$VAR_DIR`/прежних пользовательских данных (токен,
`config.cfg`, `sync.state`, маркер bisync), которые на свежей установке отсутствуют.
**Безопасный дефолт при неопределённости — вести себя как апгрейд (ADVISORY, не
делать ненулевой выход `postinst`):** ошибочно потерять «чистый отказ» на свежей
установке дешевле, чем непредсказуемо упасть на апгрейде в неизвестное поведение
DSM (§3.3). Точные имена `SYNOPKG_*` фиксируются разведкой (§12-6) до кода.

### 5.1. Санитизированный лог (безопасен по построению)
- Пишем подробный лог проверок (что/почему упало, версии, arch, пути в общем
  виде). **Никогда** не пишем содержимое `rclone.conf`/токена/секретов (канон).
  Лог трогает только структуру/arch → безопасен для показа человеку.
- **Единственное расположение (решено §10-4, §10-4a):**
  `$VAR_DIR/logs/install-check.log`. Копии в `/tmp` **НЕТ**. Пишет **только
  `postinst`** — `preinst` на свежей установке ещё не имеет `$VAR_DIR`, поэтому
  при FAIL он лишь печатает причину в stderr (§4.2, §5.2), персистентный лог не
  ведёт.
- **Single-run (перезапись каждый раз):** в начале `postinst`, до проверок,
  старый файл удаляется (`rm -f`) и пишется заново — лог предыдущей установки не
  накапливается (требование §10-4a). Свежая установка — файла ещё нет (no-op);
  апгрейд — затирается прошлый. `rotate_log` к нему **НЕ** применяется (это снимок
  одного прогона, а не растущий операционный лог). Удаление именно в начале
  `postinst`, а не в `preupgrade`: если апгрейд оборвётся раньше (на `preinst`),
  лог последней рабочей установки сохранится для всё ещё работающей старой версии.
- **Принятый остаточный риск (§10-4a):** при провале **свежей** установки, если
  DSM стирает `$VAR_DIR` (⚠ ВЕРИФ §12), персистентного лога не будет нигде →
  человек опирается только на ёмкий stderr (§5.2) + тело issue. На провале
  **апгрейда** `$VAR_DIR` остаётся (пакет не удаляется, §10-1 ADVISORY) → лог
  доступен.

### 5.2. Что видит человек (реалистичный канал)
Package Center покажет лишь финальные строки stderr → делаем их **ёмкими и
самодостаточными** (тем более что на сбойной свежей установке персистентного лога
может не быть — §5.1, §10-4a: имя упавшей проверки и причину пишем прямо сюда).
**Двойная запись из одного источника:** упавшая проверка + причина пишутся **и**
в `install-check.log` (как часть полного прогона, §5.1), **и** дублируются в
stderr — это не «или-или». Лог-хелпер `postinst` (напр. `fail()`) одной и той же
строкой кормит и файл, и stderr → между «что в логе» и «что показано человеку»
нет расхождения (анти-дрейф). Самодостаточность stderr нужна для единственного
случая §10-4a: при провале свежей установки лог может быть стёрт, и stderr —
единственный уцелевший след.

Пример — **вариант для апгрейда** (на свежей установке строки про лог/откат
отличаются, §5.4):

```
✗ Установка прервана: <короткая причина, напр. «arch rclone не совпадает с NAS»>.
  Подробный лог:   /var/packages/YandexDisk/var/logs/install-check.log
  Сообщить об ошибке (лог приложить):
    https://github.com/volkovpv/yandexdisk-dsm-app/issues/new?labels=install-check&title=...
  Откат: переустановите предыдущую версию .spk:
    https://github.com/volkovpv/yandexdisk-dsm-app/releases
  Ваши настройки (токен, папки) сохранены и переустановки не требуют.
```

### 5.3. GitHub issue — реалистичная форма (НЕ авто-POST)
- Авто-создание невозможно/запрещено (нет авторизации/сети/прав; запрет наружу
  без подтверждения; риск утечки в публичный issue).
- Даём **пред-заполненную ссылку** `issues/new?labels=install-check&title=...&body=...`
  (репо `volkovpv/yandexdisk-dsm-app`) + просим **приложить** файл лога вручную.
  Тело шаблона — без машинных секретов, с плейсхолдерами (модель NAS, версия DSM,
  версия пакета — их можно подставить из окружения, всё несекретное).

### 5.4. Откат к предыдущей версии — что это на самом деле
- **Свежая установка:** откатываться не к чему. Сообщение: «пакет не установлен,
  система не изменена».
- **Апгрейд:** «откат» = **ручная переустановка прежнего `.spk`** с GitHub
  Releases. Это безопасно, потому что **данные уже сохранены** `preupgrade`
  (токен/config/state/bisync-DB) и `postupgrade` восстановит-если-нет. То есть
  пользователь возвращает прежний бинарь, а его настройки на месте.
- **Не строим** пакетный авто-rollback бинаря (см. §7).

### 5.5. Идемпотентность/чистота на FAIL
FAIL-обработчик не оставляет фонового процесса (резидентного демона нет — канон)
и не создаёт задач Планировщика (их создаёт пользователь). Цель — не оставить
«битый, но якобы рабочий» пакет; на апгрейде честно сигналить статусом (§4.3).

## 6. Критика исходного предложения (точечно)

1. **«Тесты `preinst` и `postinst` → откат к предыдущей версии».** Смешаны два
   сценария и приписана DSM несуществующая способность (§3.3). Откат осмыслен
   только на апгрейде и только как ручная переустановка; `preinst` и `postinst`
   играют **разные** роли (§4).
2. **«`preinst` тестирует установку».** `preinst` не видит payload (§3.4) — он
   гейтит окружение, не «новую версию».
3. **«Авто-создать issue с логом».** Невозможно и небезопасно из install-скрипта
   (§5.3) — заменено на пред-заполненную ссылку + ручное приложение лога.
4. **«Показать подробный лог».** Канал ограничен последними строками stderr
   (§3.5) + лог может быть стёрт вместе с пакетом → добавлен ёмкий, самодостаточный
   вывод в stderr (§5.2). Копия в `/tmp` рассматривалась и **отклонена** (§10-4a):
   лог единственный — `install-check.log`, страховка — stderr-сводка.
5. **Пропущена приватность лога.** Добавлено требование «безопасен по
   построению», без секретов (§5.1, канон).
6. **Хорошее в предложении** (сохранено и усилено): идея «не дать встать битому
   пакету», «дать человеку лог и путь сообщить», «предложить вернуться к рабочей
   версии» — всё реализуемо в честной форме §5.

## 7. Почему НЕ строим кастомный rollback-движок (отвергнутая опция)

Можно было бы: в `preupgrade` стащить **старый payload** (бинарь rclone +
обёртка), в `postupgrade` по маркеру «postinst упал» восстановить его. Отвергаем:
- воюет с DSM, **удваивает payload** на 1 ГБ DS124;
- хрупко: version skew, ownership/права, гонки, маркер-handshake между скриптами;
- большой объём POSIX-кода, плохо покрываемого герметикой → риск «мёртвой» логики;
- по сути переизобретение транзакционного апгрейда — классический footgun.

Цена/риск несоразмерны выгоде: ручная переустановка прежнего `.spk` при уже
сохранённых данных (§5.4) — дешевле и надёжнее. (Решение фиксируется в §10-2.)

## 9. Почему функциональный тест синхронизации не может быть install-гейтом

1. **Нет учётных данных** — `rclone.conf`/токен заводятся **после** установки в UI
   (`settings.cgi`); тестировать синхронизацию во время установки нечем.
2. **Блокировка установки** — bisync это сеть и минуты; внутри `postinst` повесит
   прогресс-бар и может упасть по таймауту DSM. Синк уже отвязан через `setsid`.
3. **Порядок вещей** — install → настройка (UI) → потом проверка синхронизации.
   Остаётся ручным `test-on-nas-functional.sh` (или, как развитие, кнопкой
   «Проверить» в UI после настройки — отдельная тема).

## 9-bis. Судьба ручных NAS-скриптов после внедрения

Внедрение `postinst`/`preinst` по-разному влияет на два ручных скрипта.

### `test-on-nas-functional.sh` — остаётся
Install self-check **не покрывает** его домен (реальная синхронизация на
настроенном+запущенном пакете — §9). Это незаменимая ручная функциональная/e2e-
валидация перед релизом; роль не меняется. Опционально может **вобрать**
«running + remote настроен» проверки, уникальные сейчас для install-скрипта (он и
так работает на настроенном пакете).

### `test-on-nas-install.sh` — структурная часть дублируется `postinst`
`postinst` берёт на себя: arch rclone (совпадение с arch хоста, §10-8 — **не**
жёсткий aarch64), обёртка `yandex-disk version`,
пользователь `sc-yandexdisk`, каталог конфига. Уникально у install-скрипта
остаётся лишь **пост-настроечное** состояние, которое `postinst` сознательно НЕ
проверяет (§4.1): `synopkg status running` и наличие настроенного remote
(`config.cfg`/`rclone.conf`). Варианты (решение — §10-7):

- **Вариант 1 (рекоменд.) — слим + дедуп.** Убрать структурные проверки,
  дублирующие `postinst`; оставить только пост-настроечные (`running` + remote).
  Переосмыслить как «post-setup smoke». Мотив — канон запрещает копи-пейст
  контрактных значений между скриптами; структурные проверки живут в **одном**
  месте (`postinst`), иначе наборы разъедутся (дрейф).
- **Вариант 2 — ретайр + поглощение.** Удалить `test-on-nas-install.sh`, его
  уникальные проверки перенести в `test-on-nas-functional.sh`. Останется два
  артефакта: `postinst` (auto) + `functional` (manual).
- **Вариант 3 — диагностическое зеркало.** Оставить ручной re-run проверок
  `postinst` (вывод которого Package Center может проглотить), но без дрейфа:
  вынести read-only check-функции в общий sourced-хелпер рядом с `common.sh`,
  который sourcе-ят И `postinst`, И ручной инструмент. +Объём, зато дедуп
  архитектурно.

**Решение (§10-7): Вариант 2.** На завершающей фазе уникальные проверки
install-скрипта (`synopkg status running` + remote настроен) переносятся в
`test-on-nas-functional.sh`; сам functional переезжает `git mv` в `./test/`;
`test-on-nas-install.sh` удаляется. Итог — два артефакта: `postinst`/`preinst`
(auto, in-package) + `test/test-on-nas-functional.sh` (manual, e2e).

**Анти-дрейф (ключевое):** структурные install-проверки должны иметь **единый
источник** (`postinst`). Любой вариант, оставляющий их копию в ручном скрипте,
нарушает канон «не копировать значения между скриптами», если только это не общий
sourced-хелпер (Вариант 3).

**Документация:** `docs/ai-workflow.md`, `terminal-setup.md`, `development.md`,
`test.md` ссылаются на эти скрипты — обновить синхронно (часть §11 п.4).

## 12. NAS-разведка — обязательно подтвердить на железе (⚠ ВЕРИФ)

1. Точный **порядок lifecycle при апгрейде** и момент остановки/снятия старой
   версии относительно `preinst` (остаётся ли старая версия целой при
   `preinst != 0`?). — **главный неизвестный фактор.**
2. Поведение DSM при **`postinst != 0`**: чистит ли полу-распаковку на свежей
   установке (⇒ переживёт ли `$VAR_DIR/logs/install-check.log` провал свежей
   установки — критично для §10-4a); что происходит со старой версией на апгрейде.
3. **Под каким пользователем** бегут `preinst`/`postinst` (root vs `sc-yandexdisk`
   при `run-as: package`) → доступ к каталогам/логам и нужен ли `sudo -u` для
   e2e-смоука обёртки.
3a. **Когда DSM создаёт пользователя `sc-yandexdisk`** относительно `preinst`/
   `postinst` (ожидание: после `preinst`, до `postinst`) — от этого зависит, что
   проверка пользователя/обёртки строго `postinst`-only.
4. Доступность `$VAR_DIR/logs` на запись к моменту `postinst`.
5. Что именно и **сколько** stderr показывает Package Center при провале.
6. Имя переменной **детекта апгрейда** (`SYNOPKG_OLD_PKGVER` и т.п.) и какие
   `SYNOPKG_*` доступны в `preinst`/`postinst`.

**Кто и как снимает (R7).** Железо в среде разработки недоступно (сборка/тесты —
герметичны; доступ к NAS — ручной у мейнтейнера по SSH). Поэтому §12 — **ручной
runbook для человека**, не автоматизируемый шаг. Реализован одним скриптом
`test-on-nas-recon.sh` (в корне репо), снимающим всё разом; до прогонов PR-B (код)
не финализируется — §11-1.

### 12-bis. Прогоны и что наблюдать (через `test-on-nas-recon.sh`)

Единый скрипт `test-on-nas-recon.sh` работает в двух режимах: **(A)** ручной отчёт
`sudo sh test-on-nas-recon.sh report`; **(B)** тот же файл, скопированный в
`spk/scripts/{preinst,postinst,preupgrade,postupgrade}` throwaway-debug-сборки —
DSM зовёт его по basename, он логирует контекст фазы в `/tmp/yd-recon.log` + stdout
(→ `synopkg.log`). Падение по требованию: `echo <фаза> > /tmp/yd-recon.fail`. Все
факты структурные, без секретов. После сборки debug-`.spk` ставить вручную
`synopkg install <файл>.spk`. **Полная пошаговая инструкция** (что собрать, куда
закинуть, что запускать, куда заносить факты) — `docs/nas-recon-runbook.md`.

| # | Прогон / команда-триггер | Что наблюдать | Закрывает |
|---|---|---|---|
| 1 | Ручной отчёт: `sudo sh test-on-nas-recon.sh report` | arch хоста vs e_machine бинаря rclone (вердикт OK/MISMATCH); владелец и право-записи `$VAR_DIR/logs`; место на томе; смоук обёртки под `sc-yandexdisk` (нужен ли `sudo -u`); хвост `synopkg.log` | R1/§10-8, R4, Env(§4.1), R3, R5 |
| 2 | Свежая установка debug-`.spk` (триггера нет → exit 0) | снимки preinst+postinst: под кем бегут (`id`); есть ли `sc-yandexdisk` в preinst vs postinst; существует ли `$VAR_DIR` в preinst; пишется ли `logs`; набор `SYNOPKG_*` | R3, R3a, R4, §4.2 |
| 3 | Апгрейд поверх прежней версии (exit 0) | имя переменной апгрейда (`SYNOPKG_OLD_PKGVER`?) в снимке; отличие набора `SYNOPKG_*` от свежей установки | R3/§10-10, R6 |
| 4 | Свежая + `echo postinst > /tmp/yd-recon.fail` | убирает ли DSM полу-распаковку; **переживает ли `$VAR_DIR`** (сохранилась ли проба/снимок) | §12-2 → §10-4a |
| 5 | Апгрейд + `echo postinst > /tmp/yd-recon.fail` | осталась ли старая версия или пакет «битый»; что показано в Package Center | §3.2 → §10-1 |
| 6 | Апгрейд + `echo preinst > /tmp/yd-recon.fail` | **осталась ли старая версия целой и рабочей** | §12-1 (главный неизвестный) |
| 7 | любой FAIL (п.4–6) | сколько строк stderr-маркера (`RECON[...]: STDERR-MARKER-N`) реально показывает Package Center | R5 → §5.2 |

После прогонов `sudo sh test-on-nas-recon.sh report` собирает все снимки
(`/tmp/yd-recon.log`) + хвост `synopkg.log` в один вывод → перенести факты в пункты
1–6 §12 выше и удалить debug-обвязку (`preinst`/`postinst`-копии, `/tmp/yd-recon.fail`).
